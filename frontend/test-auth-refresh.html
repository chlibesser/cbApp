Auth State Persistence Test - V1 vs V0 Comparison

Änderungen basierend auf V0 Analyse

Problem: V1 machte aggressive Auth-Validation bei Page Refresh mit Race Conditions

Lösung: V0's bewährten Ansatz adaptiert:

  • ✅ Auth-Initialization von main.ts nach App.vue verschoben
  • ✅ Router Guards verwenden jetzt Store-State statt API-Validation
  • ✅ Lightweight initialize() - kein automatischer API-Call
  • ✅ User-Data wird erst nach stabilem App-Mount geladen

V0 (Alte App) - Bewährte Patterns:

  • Auth Init: authStore.initAuth() in App.vue onMounted
  • Simple initAuth: Setzt nur Authorization Header
  • Router Guard: Prüft lokalen isAuthenticated computed
  • Keine Auto-Validation: Kein API-Call bei Page Refresh
  • Separate Tenant Init: tenantStore.initTenant()

V1 (Neue App) - Adaptierte Implementation:

  • Auth Init: authStore.initialize() in main.ts + User-Data in App.vue
  • Lightweight initialize: Lädt nur Token aus localStorage
  • Router Guard: Verwendet authStore.isAuthenticated
  • Delayed User-Data: API-Call erst nach App-Mount
  • Error Handling: Graceful Fallback bei Auth-Fehlern

Test-Szenarien für Page Refresh:

  1. ✅ Login → Navigation → Page Refresh → Sollte eingeloggt bleiben
  2. ✅ Authenticated Route → Page Refresh → Sollte nicht zum Login umleiten
  3. ✅ Token expired → Page Refresh → Sollte graceful logout machen
  4. ✅ No Token → Protected Route → Sollte zu Login umleiten
